# HarnessDock v0.2.0 Development Plan

## Release intent

v0.2.0 starts the transition from an Electron-only public desktop package to a host-neutral HarnessDock platform.

The fixed product roles are:

- **Tauri Next-Gen** — default future desktop release host and the only host intended for public v0.2.0 desktop installers after promotion gates pass.
- **Electron Stable / LTS** — compatibility reference and rollback host. It remains buildable and tested but is not the default v0.2.0 public installer target.
- **Perry Experimental** — native/AOT research, performance benchmark, and future HarnessDock Lite exploration. Perry failures must not block official Tauri releases.
- **VS Code / Cursor** — extension host using the same runtime contracts.

This is **contract parity**, not framework-API parity. Business behavior, official Harness UI, dsh runtime/configuration, sessions, plugins and data remain shared; framework-native APIs are implemented behind host adapters.

## Non-negotiable invariants

1. Do not fork or rewrite the official DeepSeek Harness Web UI.
2. Official Harness state stays in `~/.dsh` and is shared across supported hosts.
3. Host-owned browser/cache/update state is isolated per host.
4. Desktop hosts use `LocalRuntimeProvider`; mobile hosts use `RemoteRuntimeProvider` and never download/execute the desktop Node+dsh runtime.
5. No WebView receives unrestricted shell/runtime-management permissions.
6. The existing Electron release line is not removed until Tauri passes the full promotion matrix.
7. Perry Experimental is isolated from the official release gate.

## v0.2.0 implementation strategy

### M0 — Contract and version foundation

- Move all workspace development versions to `0.2.0`.
- Add Tauri desktop/mobile host profiles.
- Separate `channel` (`stable`, `next`, `experimental`) from `releaseRole` (`default`, `compatibility`, `experimental`, `extension`).
- Extend runtime lease ownership to Tauri while retaining the existing schema and stale-owner recovery.
- Keep capability flags pessimistic until an adapter and parity test prove the capability.

Exit gate: unit tests and version/release checks green on Windows, macOS and Linux.

### M1 — Tauri Next-Gen shell + Runtime Bridge

Use a deliberately low-risk migration path:

```text
Tauri Rust shell
  -> bundled Node runtime bridge
  -> existing LocalRuntimeProvider
  -> existing DshRuntime/download/rollback logic
  -> dsh web on 127.0.0.1:0
  -> official Harness Web UI in the Tauri system WebView
```

The bridge keeps the proven TypeScript runtime code as the source of truth instead of rewriting download, integrity, rollback and process shutdown in Rust during the same release.

Tauri Rust owns window lifecycle and never grants the remote Harness origin general shell access.

Exit gate: Tauri host compiles on Windows/macOS/Linux and can boot a system/local dsh development runtime.

### M2 — Tauri runtime distribution

Two runtime scenarios remain supported in source code:

- **Full**: Tauri + Node + pinned dsh runtime closure. This is the first v0.2 public release candidate because it is deterministic/offline on first launch.
- **Thin**: Tauri + minimal bundled Node; dsh closure is fetched and integrity-verified by the existing runtime downloader. Unlike Electron, Tauri cannot reuse its executable as Node, so Node remains part of the thin Tauri package.

Both scenarios use the same `origin.json`, integrity rules, last-known-good rollback and runtime cache contract.

Exit gate: clean-machine smoke tests prove Full offline boot and Thin first-launch download + second-launch cache reuse.

### M3 — Native Service Contract

Add narrow adapters, not framework checks in business code:

- FileService: picker, save/export, reveal
- ClipboardService
- ExternalUrlService
- NotificationService
- CredentialService
- DeepLinkService
- WindowService
- DiagnosticsService

Tauri capabilities are promoted one by one only when the adapter exists and the parity suite covers it.

Exit gate: download/export, upload/file picker, clipboard, external links, OAuth and diagnostics behave equivalently to Electron for supported flows.

### M4 — updater, signing and package formats

- Tauri updater/signature integration.
- Windows installer signing and upgrade/uninstall validation.
- macOS signing + notarization + DMG validation.
- Linux AppImage + DEB validation.
- Generate one release manifest identifying Tauri as default, Electron as compatibility, Perry as experimental.

The public GitHub Release switches to Tauri artifacts only after this milestone passes.

### M5 — real Harness parity gate

Required scenarios on each supported desktop OS:

- dsh boot and ready handshake
- official Harness UI ready
- auth/login
- create/resume session
- streaming and WebSocket reconnect
- plugin load
- MCP and Skill workflows
- workspace navigation
- file upload
- file download/export
- clipboard
- IME/keyboard shortcuts
- OAuth/external links
- restart and clean shutdown
- runtime rollback
- updater
- crash/stale-lease recovery

Tauri must pass all required rows before `com.dsh.client` is transferred from Electron LTS to the Tauri release package.

### M6 — release promotion

Only after M0-M5:

```text
v0.2.0 public desktop assets
  Windows -> Tauri installer
  macOS   -> Tauri DMG
  Linux   -> Tauri AppImage + DEB

Electron -> source-buildable LTS / compatibility CI artifact
Perry    -> experimental Actions artifact only
```

Until promotion, Tauri uses side-by-side app id `com.dsh.client.tauri.next`; Electron keeps `com.dsh.client` so development cannot overwrite the stable installed client.

## CI policy

- Shared contracts/tests: blocking for every host.
- Tauri Next-Gen: blocking for v0.2 release promotion.
- Electron compatibility: blocking when shared-core changes regress the stable reference behavior.
- Perry Experimental: non-release-blocking; failures are tracked independently.
- Mobile: independent preview/experimental matrix; it cannot block v0.2 desktop stabilization.

## Risk assessment

| Area | Difficulty | Primary mitigation |
| --- | --- | --- |
| Host/Runtime contracts | Medium | adapters + tests; no framework branching in business logic |
| Tauri shell | Medium | use system WebView and keep Rust surface narrow |
| Runtime lifecycle | Medium-high | reuse LocalRuntimeProvider/DshRuntime first |
| Thin distribution | High | bundle Node; reuse verified dsh downloader/cache |
| File/download parity | High | Native Service adapters + OS E2E |
| WebView parity/IME/OAuth | High | real Harness test matrix, not mock-only tests |
| Signing/updater | High | isolated release workflow and clean-machine validation |
| Perry compatibility | High/variable | experimental lane never blocks Tauri release |

Overall v0.2.0 implementation difficulty is **7/10**. The architecture itself is tractable; cross-platform packaging and behavioral parity are the critical path.

## Definition of done

v0.2.0 is complete only when:

1. Tauri is the default release host in code and release metadata.
2. Windows/macOS/Linux Tauri packages pass the real Harness parity matrix.
3. Official Release assets contain the validated Tauri installers/packages.
4. Electron remains buildable as LTS/compatibility fallback from the same commit.
5. Perry remains buildable/testable in an isolated Experimental lane without blocking release.
6. No user Harness data migration is required when moving between Electron and Tauri.
