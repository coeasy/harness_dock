# HarnessDock v0.2.0 全新架构重构方案（最终定稿）

> 状态：**v0.2.0 新架构唯一有效设计基线**  
> 日期：2026-09-03  
> 目标：以最新产品定位重新设计 HarnessDock，不兼容旧 Host Core、旧 IPC、旧控制页、旧 Electron 方案或历史 v0.2.x 过渡实现。  
> 参考项目：`dsh-tauri-desk/deepseek-harness-desktop` 仅作为设计参考，不作为实现模板。

---

## 0. 文档结论

v0.2.0 不继续在现有 Shell-first 代码上叠加补丁，而是重新定义 HarnessDock：

**HarnessDock 是 DeepSeek Harness 的跨平台 Native Host Kernel，而不是另一个 Harness UI。**

桌面端唯一主链路：

```text
Native Process
  -> Host Kernel
  -> Runtime Actor
  -> pinned dsh Runtime
  -> Runtime Lease
  -> Harness Surface
  -> Harness Web
  -> optional Shell Extension
```

移动端唯一主链路：

```text
Mobile Tauri
  -> HTTPS Gateway
  -> authenticated remote session
  -> desktop/server Runtime
```

新架构明确删除以下旧思路：

- 不再为旧 IPC / Host Bridge v1 做兼容层。
- 不再保留隐藏 `main` 控制页作为常驻第二套 UI。
- 不再用多个 `AtomicBool` 拼装 Runtime/Gateway 生命周期。
- 不再让 Tauri command、Tray、Menu、Shell 分别直调具体 Runtime/Gateway 实现。
- 不再把 Node Gateway sidecar 作为默认 Gateway 实现。
- 不再保留 Electron 相关运行、更新、测试、发布逻辑。
- 不再要求新配置读取或迁移旧 Host 状态文件；v0.2.0 使用新的独立 schema/namespace。

旧 `docs/upgrade-refactor-plan*.md`、旧 `docs/plan/v0.2.x-*` 仅作为历史记录，不再约束本方案。

# 1. 为什么参考项目不能直接照搬

参考项目值得吸收的机制：

1. Tauri command 与业务服务分离。
2. 生命周期逻辑集中到 workflow/service，而不是散落在 UI。
3. 进程必须有明确 owner。
4. 关键切换需要互斥或事务边界。
5. Window/Menu/Tray 属于 desktop adapter，而不是业务核心。
6. 启停、健康检查、清场、自愈应是 Native Host 职责。

但直接复制仍然存在以下问题：

| 参考机制 | 问题 | HarnessDock 新方案 |
| --- | --- | --- |
| `bridge -> service -> workflow` | workflow 容易继续膨胀成 God Object | Actor + Reconciler + Policy 分离 |
| 全局 Status/Mutex | 状态与真实资源可能短暂不一致 | Actor 内唯一状态 + Snapshot Watch |
| `LAUNCH_GUARD` 等 bool | 多资源组合仍会出现竞态窗口 | 串行 Actor mailbox + generation |
| 核心切换大锁 | 大锁会阻塞无关窗口操作 | 资源级 actor + lease，不使用全局业务锁 |
| PID/Handle 全局登记 | 多处可读取/修改 ownership | Child 句柄只存在于 owning actor |
| 前端显式 orchestrate | UI 变成业务流程的一部分 | Native desired-state 启动 |
| 数十个 Tauri commands | 权限面和 API 漂移持续扩大 | 单一 v2 dispatch + typed command |
| 常驻管理面板 | 与 Harness 主界面竞争产品定位 | Diagnostics/Gateway/Recovery 按需创建 |

因此，本项目最终架构不是“参考项目结构的优化版”，而是从 **资源所有权、状态机、依赖关系、协议边界** 四个基础问题重新设计。

# 2. 三轮架构推演

## 2.1 第一轮：经典分层 Host

第一轮候选结构：

```text
Tauri Adapter
  -> Bridge
  -> Application Workflow
  -> Runtime/Gateway/Window Services
```

优点：

- 比当前模块互相直调更清晰。
- Tauri command 变薄。
- 可以快速整理 lib.rs。

第一轮审计发现仍不够好：

1. Workflow 会逐渐吸收所有跨服务流程。
2. Runtime restart 内仍需同时协调 Runtime、Gateway、WebView。
3. 全局生命周期锁仍然存在。
4. stop/start 在长时间 blocking spawn 时不易取消。
5. Snapshot 只是“观察多个 flag 后推导”，不是资源真相。

**结论：第一轮方案淘汰，不作为最终架构。**

---

## 2.2 第二轮：Actor + 显式状态机

第二轮将每个长生命周期资源改造成 Actor：

```text
Host Controller
  |- RuntimeActor
  |- SurfaceActor
  |- GatewayActor
  |- UpdateActor
  `- DiagnosticsActor
```

每个 Actor：

- 只有一个 mailbox。
- 只有 Actor 自己能持有和修改资源句柄。
- 命令串行处理。
- 状态变化发出 typed event。
- 每次启动生成新的 generation。
- 长启动任务支持 cancellation。

解决的问题：

- 删除 Start/Stop/Restart 多 bool 竞争。
- Child ownership 唯一。
- 无需共享 `Mutex<Option<Child>>` 给多个模块。
- stale callback 可以通过 generation 丢弃。

第二轮审计仍发现三个不足：

1. Host Controller 仍可能成为新的 God Object。
2. Runtime/Gateway/Surface 的依赖关系如果写成手工顺序，后续仍会反复出现断链。
3. Actor 之间如果互相直接调用，会形成隐式环依赖。

**结论：Actor 保留，但跨 Actor 编排继续升级。**

---

## 2.3 第三轮：Resource Graph + Lease + Reconciler（最终方案）

最终架构采用：

- Actor：拥有资源。
- Lease：表达资源依赖。
- Desired State：表达产品意图。
- Reconciler：使当前状态收敛到目标状态。
- Policy：决定失败后的降级策略。
- Protocol：统一所有 UI / Shell / Tray 的命令入口。

核心资源图：

```text
                 +----------------+
                 |   App Session  |
                 +-------+--------+
                         |
                    Host Kernel
                         |
                desired / reconcile
                         |
        +----------------+----------------+
        |                |                |
   RuntimeActor     SurfaceActor      UpdateActor
        |                ^                |
        | RuntimeLease   |                |
        +----------------+                |
        |
        +--------------> GatewayService
                   RuntimeLease
```

关键原则：

- **Runtime 是唯一基础资源。**
- Surface 和 Gateway 不能只保存 URL，而必须持有 Runtime Lease。
- Runtime generation 改变时，旧 Surface/Gateway lease 自动失效。
- Reconciler 只表达“要什么”，Actor 决定“怎么做”。
- Window minimize/maximize/close 不经过资源全局事务，始终保持即时响应。

这就是 v0.2.0 最终架构。

# 4. Host Kernel

`HostKernel` 是进程内唯一应用核心句柄，但不是 God Object。

建议接口：

```text
HostKernel
  dispatch(command, context) -> HostResponse
  snapshot() -> HostSnapshot
  subscribe() -> HostEvent stream
  set_desired_state(intent)
  shutdown()
```

内部只持有：

- actor handles
- event bus
- reconciler
- policy engine
- settings store
- immutable build manifest

Kernel 不直接保存 `Child`、WebviewWindow、Gateway socket 或 updater handle。

# 5. Runtime Actor

## 5.1 状态机

```text
Stopped
  -> Preparing
  -> Starting
  -> Probing
  -> Ready
  -> Degraded
  -> Stopping
  -> Stopped

任何阶段 -> Failed
任何启动阶段 -> Cancelling -> Stopped
```

禁止出现：

- Starting + Stopping 同时为 true。
- Restarting 额外作为独立 bool。
- 同时存在两个“当前 Runtime”。

Restart 定义为一个 intent：

```text
Restart(mode)
  -> invalidate current generation
  -> stop owned process
  -> create next generation
  -> start(mode)
```

## 5.2 Runtime Generation

每次启动生成：

```text
RuntimeGeneration {
  id: u64,
  nonce: 256-bit random,
  mode: Normal | Quarantine | Safe,
}
```

ready handshake 必须返回 generation nonce。

新的 ready v2：

```json
{
  "schemaVersion": 2,
  "generation": 42,
  "nonce": "...",
  "pid": 1234,
  "host": "127.0.0.1",
  "port": 43123,
  "dshVersion": "...",
  "url": "http://127.0.0.1:43123/?token=..."
}
```

校验条件：

- nonce 匹配当前 launch attempt。
- generation 匹配。
- PID 匹配 owned process。
- host 必须精确 `127.0.0.1`。
- port 非 0。
- URL origin 与 host/port 完全一致。
- URL 不允许 username/password。
- token 永远不进入公共日志。

## 5.3 进程所有权

Runtime Actor 是唯一 child owner。

Windows：

- 优先使用 Job Object 管理整棵 Node/dsh 子进程树。
- Job 配置 `KILL_ON_JOB_CLOSE`。
- 不依赖全局 PID 扫描作为正常退出机制。

Unix：

- 独立 process group。
- 先 TERM，超时后 KILL。

PID 扫描只用于 diagnostics/repair，不进入主生命周期。

## 5.4 Runtime Image

v0.2.0 默认使用不可变 Full Runtime：

```text
runtime-manifest.json
  nodeVersion
  dshVersion
  dshCommit
  platform
  arch
  criticalFiles[]
  hashes[]
```

规则：

- Host 不在启动时自动下载另一套 system Node。
- bundled Node 是默认唯一运行时。
- system Node 只作为 developer override，不属于正式产品主路径。
- Runtime 资源由 Candidate 构建阶段校验完整性。
- 应用更新与 Runtime 更新在同一 immutable release 中完成。

# 6. Runtime Lease

`RuntimeLease` 是最终架构最关键的新对象。

```text
RuntimeLease {
  generation,
  pid,
  origin,
  privateAppUrl,
  dshVersion,
}
```

注意：

- `privateAppUrl` 可以包含一次性 token，只能在 host-core 内部使用。
- UI snapshot 只能得到 `displayOrigin`，不得得到 token URL。
- Surface/Gateway 必须持有 generation 一致的 Lease。

这样可以彻底替代“启动 Gateway 后再次比较 URL 是否变化”之类的补丁逻辑。

# 7. Surface Actor

## 7.1 不再保留隐藏 Main Window

新模型只有四类 Surface：

1. `HarnessSurface`：主业务界面。
2. `RecoverySurface`：启动失败时动态创建。
3. `GatewaySurface`：用户主动打开。
4. `DiagnosticsSurface`：用户主动打开。

不存在常驻隐藏控制页。

## 7.2 Harness Surface 状态机

```text
Absent
 -> Creating
 -> Loading(leaseGeneration, navigationId)
 -> Visible
 -> Hidden
 -> Closing
 -> Absent

Loading -> Failed -> RecoverySurface
```

规则：

- WebView 必须绑定 Runtime Lease。
- navigation callback 必须同时匹配 generation + navigationId。
- stale Finished event 直接忽略。
- 只允许当前 Runtime exact origin。
- Runtime generation 改变时旧 Surface 立即失效。

## 7.3 首屏策略

正常启动：

- 不先显示设置页。
- 不先显示管理页。
- Harness Web 才是第一个业务 Surface。
- 如果 Runtime 在很短时间内 ready，不显示 splash。
- 超过约 300ms 再显示轻量 native splash，避免闪屏。
- Harness Web first paint 后才显示窗口。

# 8. Shell Extension v2

Shell 仍支持独立发布，但它只负责**展示层**，不拥有业务流程。

建议包：

```text
@dsh/plugin-harness-shell
@harnessdock/host-sdk
```

Shell 能力：

- minimize
- toggle maximize
- close/hide
- refresh Harness Web
- restart Runtime
- safe start
- clear quarantine
- open Gateway
- open Diagnostics
- check/install update
- quit

Shell 失败不影响 Runtime/Harness Web。

## 8.1 Shell Handshake

Shell 插件加载后必须执行：

```text
host.describe()
 -> apiVersion
 -> productVersion
 -> sessionId
 -> capabilities
 -> snapshot
```

如果 800ms 内没有完成 Shell handshake：

- Host 不把它视为 Runtime 失败。
- 恢复原生 window decorations。
- Menu/Tray 继续可用。

## 8.2 不兼容旧 Host Bridge

v0.2.0 直接启用 Host API v2。

不提供：

- apiVersion=1 compatibility shim
- command alias
- legacy payload conversion

# 9. Host Protocol v2

## 9.1 单一 IPC 入口

不再暴露几十个业务 Tauri command。

唯一业务入口：

```text
host_dispatch(request)
```

Request：

```json
{
  "apiVersion": 2,
  "requestId": "...",
  "sessionId": "...",
  "command": "runtime.restart",
  "payload": {}
}
```

Response：

```json
{
  "ok": true,
  "data": {},
  "snapshotRevision": 128
}
```

错误：

```json
{
  "ok": false,
  "error": {
    "code": "RUNTIME_START_FAILED",
    "message": "...",
    "retryable": true,
    "action": "retry-safe"
  }
}
```

## 9.2 命令域

```text
window.*
web.*
runtime.*
gateway.*
diagnostics.*
update.*
app.*
```

## 9.3 Event

统一 `HostEvent`：

```text
RuntimeChanged
SurfaceChanged
GatewayChanged
RecoveryChanged
UpdateChanged
OperationProgress
OperationFailed
HostShuttingDown
```

UI 不轮询多个 Native 状态源，而是：

1. 首次 `host.describe()` 获取 Snapshot。
2. 后续订阅 Event。
3. 必要时按 revision 重新 snapshot。

# 10. Capability Broker

远程 Harness Web 不获得通用 Tauri 权限。

每次 Harness Surface 创建一个短生命周期 `BridgeSession`：

```text
BridgeSession {
  sessionId,
  windowLabel,
  runtimeGeneration,
  runtimeOrigin,
  capabilitySet,
}
```

每个 dispatch 必须验证：

- session 存在。
- source window label 正确。
- runtime generation 未变化。
- 当前 WebView origin 仍等于 session origin。
- command 在 capability set 内。

导航、reload、Runtime restart、window destroy 都会撤销旧 session。

即使 Tauri 静态 remote capability 需要允许 `127.0.0.1:*`，其他本地网页也无法仅凭 origin 获得有效 Host Session。

# 11. Gateway v2：Rust Native Service

最终方案不再以 Node sidecar 作为默认实现。

`gateway-core` 直接运行在 Rust/Tokio：

```text
GatewayActor
  -> GatewayServer task
  -> Pairing service
  -> Session store
  -> HTTP/WebSocket reverse proxy
  -> RuntimeLease
```

收益：

- 删除第二个 Node 子进程。
- 删除 Gateway ready.json。
- 删除本地 admin API。
- 删除 admin token。
- 删除 sidecar start/stop 竞态。
- Gateway 与 Runtime generation 原生绑定。
- graceful shutdown 由 task cancellation 完成。

## 11.1 Gateway 状态

```text
Stopped
 -> Starting
 -> Ready
 -> Draining
 -> Stopped

任何阶段 -> Failed
```

## 11.2 Runtime 依赖

Gateway 启动必须传 RuntimeLease。

Runtime generation 失效时：

```text
Lease invalidated
 -> stop accepting new sessions
 -> drain active proxy requests
 -> close server
 -> Gateway=Stopped
```

不再通过“再次检查 upstream URL 是否相同”判断有效性。

## 11.3 Pairing

- 8 位一次性 pairing code。
- code 只存内存。
- 短 TTL。
- rate limit。
- 成功后生成高熵 session token。
- server 只持久化 session token hash，不存明文 bearer token。
- revoke/revoke-all 直接操作 native session store。

## 11.4 移动端

移动端永远不启动本地 Node/dsh Runtime。

```text
Mobile
 -> health
 -> pair
 -> HttpOnly session
 -> remote Harness Web
```

移动端远程页面永远没有桌面 Host Capability Broker session。

# 12. Recovery Policy Engine

Recovery 不再散落在 Runtime start 函数内部。

统一：

```text
RecoveryPolicy.evaluate(FailureContext) -> RecoveryDecision
```

候选策略：

```text
Normal
 -> VersionScopedQuarantine
 -> DiagnosticIsolation
 -> SafeOverlay
 -> RecoverySurface
```

规则：

- 永远不修改用户真实 DSH 配置。
- 所有隔离都通过 ephemeral overlay/patch。
- quarantine 必须绑定 dsh version + plugin identity/version。
- quarantine 有 TTL。
- dsh/plugin 版本发生变化时旧 quarantine 自动失效。
- ambiguous failure 不进行无限插件二分重启，直接 SafeOverlay。
- 最多有限次数 recovery attempt，禁止启动死循环。

RecoverySurface 提供：

- Retry Normal
- Safe Start
- Clear Quarantine
- Open Diagnostics
- Export Support Bundle
- Quit

示例：

# 15. 更新与发布体系

## 15.1 Build Manifest

每个候选构建都生成：

```json
{
  "productVersion": "0.2.0",
  "gitSha": "...",
  "hostApiVersion": 2,
  "runtime": {
    "nodeVersion": "...",
    "dshVersion": "...",
    "dshCommit": "..."
  },
  "shell": {
    "version": "...",
    "sha256": "..."
  },
  "platform": "windows-x86_64"
}
```

## 15.2 版本模型解耦

从 v0.2.0 开始区分：

- Product Version：`0.2.0`
- Host API Version：`2`
- dsh Runtime Version：独立固定
- Shell Package Version：独立 semver
- Gateway Protocol Version：独立 schema

首个正式版本可以都显示 0.2.0，但不再用“所有组件版本必须永远相等”作为架构约束。

## 15.3 Candidate -> Release

```text
commit
 -> unit/contracts
 -> host-core concurrency tests
 -> tauri platform smoke
 -> candidate build
 -> artifact hash manifest
 -> release assembly from exact candidate
 -> signed desktop updater metadata
```

Release 不重新 build。

正式 Release 只能复用 exact candidate artifact。

## 15.4 Desktop Update

- 继续使用 Tauri signed updater。
- update check 在 Harness 主界面 visible 后异步启动。
- update check/install 永远不阻塞正常启动。
- install 前 Kernel 进入 Quiescing。
- Gateway 先 drain。
- Runtime 再 stop。
- Surface 最后 close。

## 15.5 Android / iOS

v0.2.0 延续当前产品决策：

- Android candidate 不增加仓库内 release-signature verification gate，不要求 `ANDROID_KEY_*`。
- APK/AAB 必须通过非空、非 debug、包体/Native library 基础门禁后上传。
- iOS 当前仍以 Simulator Remote Client 为开发/验证产物；App Store/physical-device distribution 不纳入本轮完成条件。

# 17. 测试策略

## 17.1 Pure State Machine

Runtime/Gateway/Surface 状态迁移必须可以纯函数测试。

## 17.2 Actor Sequence Test

随机命令序列验证 invariant：

1. 同时最多一个 owned Runtime generation。
2. Gateway lease generation 必须等于当前 Runtime。
3. Surface lease generation 必须等于当前 Runtime。
4. shutdown 之后不能接受 start/restart。
5. shell failure 不得影响 Runtime Ready。
6. stale callback 不得使旧 Surface 重新 visible。
7. failed/cancelled startup 不得遗留 child。

建议使用 property-based test 覆盖大量顺序组合。

## 17.3 Failure Injection

必须人工注入：

- Node 不存在
- dsh 入口损坏
- ready nonce 不匹配
- ready PID 不匹配
- Runtime 早退
- WebView load timeout
- Shell injection failure
- plugin crash
- Gateway bind failure
- Runtime restart during Gateway traffic
- quit during Runtime Starting
- updater unavailable
- tray/menu unavailable

所有失败都必须保证 Host 仍有确定的用户出口。

# 21. 最终退出流程

```text
Quit Intent
 -> DesiredState = Stopped
 -> reject new business intents
 -> invalidate bridge sessions
 -> Gateway drain/stop
 -> Surface close
 -> Runtime cancel/stop
 -> flush bounded diagnostics
 -> Tauri exit
```

任何阶段重复 quit 都必须幂等。

# 22. 最终验收标准

架构层：

- `lib.rs` 不含业务 workflow。
- Runtime/Gateway/Surface 都是明确 Actor/state machine。
- 不存在 runtime_starting/runtime_restarting/runtime_stopping 组合式状态。
- 不存在隐藏 `main` 常驻控制页。
- 不存在默认 Node Gateway sidecar。
- 不存在 v1 Host Bridge compatibility shim。
- Shell/Tray/Menu 不直接调用 Runtime/Gateway 具体实现。
- Runtime child 只有一个 owner。
- Gateway/Surface 依赖 RuntimeLease。

安全层：

- Harness Web 只有短生命周期 capability session。
- stale generation/session 全部拒绝。
- public snapshot 不包含 token URL。
- pairing/session secrets 不进入日志。
- Gateway session token 服务端只保存 hash。

产品层：

- 启动直接进入 Harness Web。
- Shell 失败仍可通过 native decorations 使用客户端。
- plugin failure 不能使 Host 无法退出/诊断。
- Gateway failure 不影响 Harness Web。
- updater/tray/menu failure 不影响 Harness Web。

工程层：

- final head 的正式 CI 全绿。
- 至少连续 3 轮完整测试无新增错误。
- Windows/macOS/Linux desktop smoke 通过。
- Android/iOS remote-client smoke 通过。
- Candidate artifact hash 与 Release 完全一致。

# 23. 最终决定

v0.2.0 不再定义为“Shell-first 分支上的一次增强”，而定义为：

> **一个以 Resource Ownership、Actor State Machine、Runtime Lease、Desired-State Reconciliation、Capability Broker 为核心的 Tauri Native Host Kernel。**

参考项目提供的是“Native service/workflow 要成为主导”的启发；HarnessDock 最终向前一步，把 workflow 本身也拆掉，使用资源 Actor 与依赖图保证主链路不会再靠大量局部 guard、回调补丁和隐式顺序维持正确性。

后续代码实现、测试、CI、文档都应以本文作为 v0.2.0 唯一架构基线。
