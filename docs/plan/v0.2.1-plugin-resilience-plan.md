# HarnessDock v0.2.1 Plugin Fault-Containment Plan

## Goal

A third-party or user-added plugin is untrusted extension code from the host's point of view. A missing, outdated, incompatible, slow, or crashing plugin must never make the HarnessDock host application unavailable.

The invariant for v0.2.1 is:

> Plugin failure may reduce plugin functionality, but it must not terminate the HarnessDock shell, corrupt user configuration, or create an infinite restart loop.

Official `@deepseek-ai/*` rows and HarnessDock's `embedded-client` bridge are never automatically quarantined by the third-party recovery policy.

## Failure containment layers

### 1. Host/process containment

The Electron/Tauri host lifecycle is independent from the dsh Runtime lifecycle.

- Host initialization failures may still be fatal.
- Runtime/plugin startup failures are non-fatal host events.
- Electron keeps Diagnostics, tray, update and retry controls available even if dsh cannot start.
- Tauri keeps its local shell available and reports Runtime failure/degraded state instead of closing the application.

Runtime states are explicit: `connecting`, `ready`, `degraded`, `crashed`, `restarting`, `stopped`.

### 2. Normal boot first

When no valid quarantine exists, HarnessDock first starts dsh with the user's normal configuration. Healthy third-party plugins are never disabled pre-emptively.

### 3. Boot-free discovery and safe-mode recovery

If normal dsh startup fails and packaged recovery is enabled:

1. Stop the failed child process tree.
2. Run `dsh --dump-config` to inspect effective rows without evaluating plugins.
3. Separate official/HarnessDock rows from external rows.
4. Record rows named by the diagnostic as `suspectedPlugins`.
5. Build a recovery patch that disables the complete external set for this recovery boot.
6. Start dsh again with the embedded bridge plus the temporary recovery patch.

The complete external isolation set is intentional: upstream startup errors often mention only the first incompatible plugin. Isolating only that row can make the retry fail on a second stale plugin.

The recovery patch is stored only in the per-process temporary directory. User dsh configuration is never rewritten.

### 4. Expiring quarantine circuit breaker

A successful safe-mode recovery proves that the external plugin set caused or participated in the startup failure. HarnessDock stores a host-owned quarantine record containing only plugin ids and recovery metadata.

Properties:

- scoped to the exact dsh version;
- expires automatically after 24 hours by default;
- invalid/corrupt records are ignored and removed;
- a dsh version change invalidates the record;
- quarantine never edits the user's dsh configuration;
- a quarantined boot that fails clears the stale quarantine and retries normal configuration;
- the user can clear quarantine explicitly and retry.

This prevents every launch from intentionally reproducing the same known plugin crash while still allowing repaired/upgraded plugins to return automatically.

## Structured recovery diagnostics

Runtime exposes a structured recovery snapshot:

- `active`
- `source`: `none | startup-failure | quarantine`
- `isolatedPlugins`
- `suspectedPlugins`
- `reason`: `diagnostic-match | ambiguous`
- `quarantineExpiresAt`

The host displays degraded mode explicitly. Recovery is never silently reported as fully healthy.

Raw startup output is not persisted in quarantine. Existing log redaction remains responsible for transient diagnostics.

## Crash/restart budget

Plugin recovery and process crash recovery are separate mechanisms.

- Plugin recovery performs one bounded safe-mode boot.
- Runtime process supervision uses bounded exponential backoff.
- Repeated crashes exhaust the automatic restart budget and leave the host in `degraded` mode with manual retry/Diagnostics available.
- No recursive relaunch loop is allowed.

## Fault matrix

| Fault | Expected behavior |
| --- | --- |
| One incompatible third-party plugin | normal boot fails, safe mode starts, plugin isolated, host stays usable |
| Multiple incompatible plugins | all external rows isolated in one recovery boot |
| Official plugin appears in diagnostic | official row is not automatically quarantined by external policy |
| `embedded-client` bridge | never selected as external recovery candidate |
| `--dump-config` fails | Runtime reports failure; host shell stays alive in Diagnostics mode |
| Safe-mode boot also fails | Runtime remains unavailable/degraded; host does not exit |
| Valid quarantine on next launch | safe mode starts directly without reproducing known plugin crash |
| Quarantine expired | normal configuration gets a fresh attempt |
| dsh version changed | previous quarantine is invalidated |
| Quarantined boot fails | quarantine is cleared, normal/safe recovery policy continues |
| Runtime crashes repeatedly after ready | bounded restart budget, then degraded shell |

## Verification gates

A v0.2.1 replacement is publishable only when all gates are green for the exact same `main` SHA:

1. workspace tests on Windows, Linux and macOS;
2. plugin recovery/quarantine tests;
3. Electron host/runtime source checks;
4. Tauri Rust recovery tests;
5. candidate runtime preparation for win-x64, linux-x64, mac-x64 and mac-arm64;
6. Windows NSIS candidate;
7. Linux DEB and AppImage candidates;
8. macOS x64 and arm64 DMGs;
9. Android APK/AAB;
10. iOS simulator package;
11. `candidate-gate` success;
12. same-SHA main `ci` success;
13. release assets assembled with non-empty files and `SHA256SUMS`.

The existing public v0.2.1 remains available until these gates pass. Same-version replacement updates the tag/assets only after candidate and CI validation.
