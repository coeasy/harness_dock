# HarnessDock v0.2.0 Embedded Runtime Tooling Contract

> Status: active implementation supplement to `docs/v0.2.0-architecture-five-round-final.md`.
>
> Distribution invariant: desktop installers contain Node + pinned dsh and do not download either on first launch.

## 1. Why a compact Node image still needs pnpm

The pinned upstream dsh CLI implements profile-plugin management as a thin forwarder to `pnpm`:

```text
dsh plugin --profile <name> add/remove/update ...
  -> spawn pnpm in the profile directory
  -> reconcile installed dsh.bundle dependencies
```

Therefore a Runtime image that can launch Harness Web but has no `pnpm` would be functionally incomplete for HarnessDock's plugin-management product path.

HarnessDock must not solve this by keeping Node's full npm/corepack developer payload. Instead the Runtime contains a small, explicitly pinned package-management tool layer.

## 2. Final Runtime tooling layout

```text
dsh-runtime/
  node.exe                  # Windows
  # or bin/node             # macOS/Linux
  LICENSE
  node_modules/
    @deepseek-ai/dsh/
    ... exact dsh production closure ...
  tools/
    bin/
      pnpm.cmd              # Windows shim
      pnpm                  # Unix executable shim
    pnpm/
      package.json
      node_modules/
        pnpm/               # exact pinned pnpm distribution
  manifest.json
```

The shim always runs pnpm with the Node binary embedded in the same Runtime image. It does not depend on system Node, system pnpm, Corepack download, or a user-modified shell environment.

Pinned tooling for v0.2.0:

```text
pnpm 10.12.1
```

The pin follows the HarnessDock workspace package-manager version unless a later compatibility test proves another exact version is required.

## 3. Build-time behavior

The Full Runtime pipeline is:

```text
prepare official Node + pinned dsh production closure
 -> install target-native optional packages
 -> prune dsh production payload
 -> embed pinned pnpm tool in isolated tools/pnpm root
 -> generate platform pnpm shim
 -> verify pnpm --version with the prepared tool payload
 -> remove Node-bundled npm/npx/corepack/developer files
 -> verify Runtime again
 -> upload prepared Runtime artifact
 -> copy exact artifact to Tauri resources/dsh-runtime
 -> full Runtime smoke
 -> package desktop installer
```

`pnpm` is downloaded only while CI/developer tooling is **building** the installer. It is already present in the installed application before first launch.

## 4. Runtime PATH contract

The desktop adapter prepends the packaged Runtime tool directory to the environment inherited by dsh:

```text
<resources>/dsh-runtime/tools/bin
<resources>/dsh-runtime[/bin]
<existing PATH>
```

This is required because upstream dsh invokes the literal command `pnpm` for profile-plugin management.

The primary Harness startup does not depend on pnpm. If the optional tool-path setup fails unexpectedly, Harness Web remains fail-open; Candidate validation must prevent such an incomplete Runtime from being published.

## 5. What is pruned

Node's official developer distribution may remove:

- npm / npx wrappers;
- Corepack wrappers and package payload;
- Node-bundled npm package tree;
- headers;
- man pages and general share/docs content;
- install helper scripts;
- README / CHANGELOG.

It must retain:

- Node executable;
- Node license;
- pinned dsh production closure;
- target-native dsh dependencies;
- bundled pnpm tool;
- pnpm shim;
- Runtime manifest.

## 6. Manifest contract

A prepared Runtime records at least:

```text
runtimeEmbedded = true
firstLaunchRuntimeDownloadRequired = false
pnpmEmbedded = true
pnpmVersion = 10.12.1
pluginManagementReady = true
```

Future Round 2 manifest work will also add immutable file digests and image identity.

## 7. Validation requirements

Round 1/2 automation must prove:

1. Node+dsh exist before Tauri packaging.
2. pnpm package + shim exist before Runtime artifact upload.
3. bundled pnpm reports the pinned version.
4. Node pruning does not remove the dsh production closure or bundled pnpm.
5. packaged dsh sees the embedded tool directory in PATH.
6. normal first startup performs no Node/dsh download.
7. `dsh plugin` no longer depends on a user-installed pnpm.

A future plugin-management smoke test should use a local fixture package so this contract can be verified without depending on the public registry during CI.
