# HarnessDock v0.2.0 对标领先客户端架构三轮优化最终方案

> 状态：**五轮 Native Host 架构之后的最终优化补充 / 三轮连续收口方案**  
> 日期：2026-09-03  
> 事实基线：PR #57 `refactor/v0.2.0-shell-first`，审计 head `cacf4faa7bc30c63d94f879661aa106de3dab82e`  
> 约束：本方案不替换 `docs/v0.2.0-architecture-five-round-final.md` 的产品定义，而是在其上继续做三轮行业对标与生产化加固。  
> 完成原则：**三轮连续执行，中途不宣称完成；只有当前 head 的架构、测试、CI、Candidate、Release 证据同时收敛后才完成。**

---

## 0. 结论先行

HarnessDock 当前方向是正确的，而且已经从普通 Tauri Web 包装器进入了“Native Host Kernel + Embedded Runtime”的架构层级：

```text
Tauri Adapter
  -> Host Protocol v2
  -> Capability Broker
  -> Desired State / Reconciler
  -> RuntimeActor / SurfaceActor / GatewayActor / UpdateActor
  -> RuntimeGeneration / RuntimeLease
  -> Harness Web
```

相比早期 Electron/隐藏控制页/多 AtomicBool/Node Gateway sidecar 方案，当前架构已经明显更接近成熟桌面客户端：

- Native Host 与 Harness Web 已经分层；
- Runtime 由安装包完整内置，不依赖首启下载；
- Runtime 生命周期开始采用 Actor + generation + cancellation；
- Window/Surface 通过 navigation id + generation 拒绝陈旧回调；
- 权限开始由 Capability Broker 统一判断；
- Gateway 已经从 Node sidecar 迁移到 Rust；
- Update 已独立成状态机；
- Release 已有 exact-main-SHA、updater signature、SHA256SUMS、immutable tag/asset 约束；
- Shell/Tray/Diagnostics/Gateway 均被定义为可选层，不允许阻塞健康 Harness Web。

但是，对照 VS Code、Chromium、Tauri v2 的安全模型以及现代软件供应链实践，当前实现仍然存在一个明显问题：

> **“目标架构”已经领先于“真实控制平面实现”。**

当前最主要的差距不是缺少更多 UI，而是：

1. Reconciler 仍是一次性 command switch，不是真正持续收敛的控制循环；
2. Host Protocol 只有 command/snapshot，没有事件流、重连补偿、幂等去重和兼容协商；
3. AppState 仍以多个 `Mutex<State>` 作为主要并发模型，Actor 还不是 mailbox/task 意义上的真正资源 owner；
4. 本地 control/diagnostics 仍有 legacy Tauri business command 绕过 Host Protocol；
5. bridge 迁移仍有重复 IPC command 残留，当前 head 还未通过全部 CI；
6. Remote Harness Web 的 capability 粒度仍偏粗；
7. Native Gateway 仍是手写 HTTP/1.1 parser + thread-per-connection，承担了不必要的协议安全风险；
8. 缺少 desktop single-instance、secondary launch handoff；
9. 缺少主动 Runtime health supervisor、crash-loop guard、suspend/resume revalidation；
10. Plugin/Profile/CLI 仍主要停留在架构文档，Host Protocol 中尚无完整管理命令；
11. Release 有签名和 digest，但还缺 SBOM + artifact provenance/attestation；
12. 可观测性主要还是 startup phase trace，缺少统一 actor transition/operation/event 诊断闭环。

因此本方案不建议继续横向堆叠新 UI，而是再做三轮纵向收口。

# 1. 当前真实架构审计

## 1.1 已经达到领先架构方向的部分

### A. Runtime 已经是独立受管资源

当前 `RuntimeActor` 已经持有：

- `RuntimeProcess`；
- `RuntimeGeneration`；
- `RuntimeLease`；
- cancellation token；
- explicit `RuntimePhase`。

这比 `starting/restarting/stopping` 多布尔值模型可靠得多。

`RuntimeGeneration` nonce 已经改为 OS CSPRNG，而不是 PID/时间哈希，这是正确的安全边界。

### B. Surface 已经绑定 generation/navigation

Harness Web 加载完成不再仅凭 `page_load` 判断成功，而是同时验证：

```text
current RuntimeLease generation
+ current Surface navigation id
+ actual WebView origin/URL
```

因此旧 generation 的异步 callback 不会误把新窗口状态覆盖掉。

### C. Tauri remote capability 已经明显收紧

当前 Harness Web 只得到：

- Host Protocol；
- event listen/unlisten；
- 最小 window primitives。

不再直接拥有 update/install/quit 等高权限命令。

### D. Runtime 分发模型已经正确

桌面安装包内置：

```text
compact Node
+ pinned dsh production closure
+ pinned pnpm tool
```

首启零 Runtime 下载，损坏时 fail-closed 到 Recovery，而不是联网下载另一套 Runtime。

### E. Release graph 已经比普通开源桌面项目严格

当前 Release workflow 已经要求：

```text
exact main SHA
-> successful same-SHA candidate
-> successful same-SHA CI
-> immutable tag
-> updater signatures
-> SHA256SUMS
-> non-empty exact asset set
```

这个方向继续保留。

# 2. 对标业内领先客户端后的主要差距

## 2.1 VS Code：独立 Host / Extension Host / Agent Host

VS Code 的成熟经验不是“所有东西都放在主进程”，而是明确拆分：

- UI renderer；
- extension host；
- shared/utility process；
- 新 Agent Host；
- local/remote host；
- 标准化 host protocol。

Agent Host 的关键特征尤其值得 HarnessDock 借鉴：

```text
Host owns state
Client is viewer/controller
Snapshot + ordered actions
Disconnect -> reconnect/resync
Host process survives a client surface
```

HarnessDock 当前虽然已经有 RuntimeActor，但 Host Kernel 本身还没有形成这种“单一真相 + event stream”模型。

### 差距

当前 `reconciler.rs` 的实现仍然是：

```text
lock desired
-> mutate field
-> match HostCommand
-> directly call harness_window/update/request_exit
```

这仍然是 command dispatcher，不是真正 reconciler。

### 需要升级

改成：

```text
Command Ingress
 -> Kernel Queue
 -> Desired State revision
 -> Reconciler Loop
 -> Resource Actor commands
 -> Actor events
 -> Actual State
 -> HostEvent stream
```

---

## 2.2 Chromium：把 renderer compromise 视为真实威胁

Chromium Site Isolation 的核心不是“网页正常情况下不会乱来”，而是：

> 假设 renderer 可能被完全攻陷，仍然限制它能触达的资源。

HarnessDock 的 Harness Web 来自本机 `127.0.0.1` Runtime，但它仍然是 Web content。只要上游 Harness、插件、依赖、XSS 或供应链出现问题，这个 renderer 都应当被视为可能不可信。

### 当前问题

`CapabilityBroker` 目前仍允许 HarnessWeb：

```text
WebReload
RuntimeRestart
RuntimeSafeMode
RuntimeClearQuarantine
GatewayManage
DiagnosticsRead
```

其中 `ShowGateway` 实际只打开 Gateway Surface，`ShowDiagnostics` 实际只打开 Diagnostics Surface，但 capability 名称分别是 `GatewayManage` 与 `DiagnosticsRead`，粒度过粗。

### 优化方向

重新拆 capability：

```text
SurfaceOpenGateway
SurfaceOpenDiagnostics
RuntimeRestart
RuntimeSafeMode
RuntimeQuarantineAdmin
GatewayAdmin
DiagnosticsRead
PluginAdmin
ProfileAdmin
UpdateCheck
UpdateInstall
AppQuit
```

Remote Harness 最多拥有低风险 intent：

```text
WebReload
RuntimeRestart
RuntimeSafeMode
SurfaceOpenGateway
SurfaceOpenDiagnostics
```

以下必须仅属于本地受信 surface/native menu/tray：

```text
RuntimeQuarantineAdmin
GatewayAdmin
DiagnosticsRead sensitive subset
PluginAdmin
ProfileAdmin
UpdateInstall
AppQuit
```

这样即使 Harness renderer 被攻陷，也只能造成有限的可恢复 DoS，而不能扩大为管理面控制权。

---

## 2.3 Tauri v2：能力应尽量绑定具体 WebView

Tauri v2 Capability 的核心是按 Window/WebView 精确收敛 IPC，官方对 remote URL 本身也明确要求谨慎。

当前 HarnessDock 已经走在正确方向，但还应继续：

- privileged local surface 明确限制为 local app origin；
- remote Harness capability 只绑定 `harness` WebView；
- 所有动态导航继续验证 current RuntimeLease origin；
- control/settings 显式拒绝导航到 remote URL；
- 不把“窗口 label 正确”作为唯一受信依据；
- 不让 local control capability 合并成一个大权限包。

Tauri 2.11.5 虽然存在 multi-webview API，但 `WebviewBuilder` 仍属于 `unstable` feature，因此本轮**不把 multi-webview 作为生产硬依赖**。

长期如果 Tauri multi-webview 稳定，可以进一步做：

```text
one native Window
  + local privileged Host Chrome WebView
  + remote zero-privilege Harness WebView
```

届时可以彻底消除“在 remote Harness DOM 中注入 privileged shell”的设计张力。

在此之前，生产主线仍采用：

```text
Native title/menu/tray = trusted
Harness WebView = untrusted
Injected Shell = fail-open convenience only
```

# 3. 当前核心缺陷与潜在问题清单

## P0 — 必须优先处理

### P0-1 Reconciler 还不是 Reconciler

**问题**：Desired State 只是被记录，然后立即调用 procedure。

**风险**：

- desired/actual 可能永久漂移；
- 同一时间多个入口仍可能以不同顺序操作资源；
- 不能自然 coalesce restart/update/quit；
- 很难做重放、恢复和模型测试。

**修复**：建立单一 `HostKernelTask` 和 reconciliation loop。

---

### P0-2 Actor 仍主要是 Mutex-wrapped state

当前：

```text
Mutex<RuntimeActor>
Mutex<SurfaceActorState>
Mutex<GatewayActorState>
Mutex<UpdateActorState>
Mutex<HostDesiredState>
```

这比 AtomicBool 好，但还不是完整 actor execution model。

**潜在风险**：

- 锁中调用/锁外调用边界容易漂移；
- poison 后恢复困难；
- 多个资源操作仍可能出现 lock ordering 问题；
- async procedure 容易出现状态与实际资源不同步。

**目标**：

```text
KernelHandle
 -> mpsc<KernelMessage>
 -> single HostKernelTask owns mutable control state
 -> actor/result messages return through generation + operation id
```

长耗时 spawn/probe/download 仍放到 worker task，但结果只能作为带 generation 的 event 回 Kernel。

---

### P0-3 Host Protocol 缺 HostEvent / revision stream

文档目标中已有 `HostEvent`，但当前 schema/实现只有：

```text
HostCommand
CommandEnvelope
ResponseEnvelope
HostSnapshot
```

本地 settings 仍每 4 秒轮询 `runtime_status`。

**问题**：

- UI 状态有最多数秒延迟；
- 无法保证事件顺序；
- 重连后不知道漏了什么；
- 多 surface 无法共享一个一致状态；
- polling 增加无意义唤醒。

**目标 Host Protocol v2.1**：

```text
HostSnapshot {
  protocol_version,
  revision,
  runtime_generation,
  ...
}

HostEvent {
  sequence,
  revision,
  operation_id,
  runtime_generation,
  kind,
  public_payload
}
```

增加：

```text
host_subscribe(last_sequence?)
host_snapshot()
```

规则：

- snapshot 是当前真相；
- event 有单调 sequence；
- sequence 缺口 -> 重新 snapshot；
- UI 不再定时 polling；
- event 不包含 token URL/session secret。

优先使用 Tauri Channel/EventTarget 定向推送。

---

### P0-4 IPC migration 未完全收口

当前 bridge 已经提供 sanitized `runtime_status` 和 destroy-on-close `shell_settings_close`，但旧模块仍保留同名 `#[tauri::command]`，已经造成真实 Rust 重复符号问题。

**修复原则**：

- `bridge.rs` 是 IPC adapter 唯一入口；
- 业务模块只暴露普通 Rust function；
- 生成 handler 中业务动作逐步只保留 `host_execute/host_snapshot/host_subscribe`；
- window primitive 可以保留专用最短路径；
- 删除 legacy command annotation，不恢复旧架构来绕过 CI。

---

### P0-5 Local control 仍绕过 Host Protocol

`apps/tauri/web/app.js` 仍直接调用：

```text
runtime_start
runtime_stop
runtime_status
gateway_host_start
gateway_host_stop
gateway_host_create_pairing
runtime_clear_plugin_quarantine
...
```

这意味着：

> NativeMenu/Tray 已经 typed intent，但本地 control 页面仍有第二条 procedure API。

**修复**：扩展 canonical Host Protocol，使 control/diagnostics 也全部通过统一 command/query/event 模型。

唯一允许保留的 direct IPC：

- 最小 window primitive；
- host protocol transport 本身。

---

### P0-6 Native Gateway 自己实现 HTTP framing

当前 Gateway 使用：

```text
TcpListener
TcpStream
manual HTTP/1.1 parser
thread per connection
io::copy duplex proxy
```

已经补了：

- 64 KiB header limit；
- 2 MiB body limit；
- duplicate Content-Length reject；
- Transfer-Encoding reject；
- origin-form target；
- connection count limit。

但是手写 HTTP proxy 仍是高风险区域。

**潜在问题**：

- hop-by-hop header 处理不完整；
- keep-alive/Connection/Upgrade 行为容易错；
- upstream/client timeout 不完整；
- thread-per-connection 在异常客户端下成本高；
- WebSocket upgrade 依赖透明字节转发，缺少正式协议测试；
- reverse proxy 场景下 peer IP 常变成 loopback，当前 IP rate-limit 可能退化成全局共享；
- response framing 不由成熟 HTTP stack 验证。

**修复**：迁移到经过广泛验证的 Rust HTTP stack：

```text
Tokio
+ hyper http1
+ explicit bounded concurrency
+ cancellation token
+ typed request/response
```

如 Harness 必须 WebSocket，再增加正式 upgrade path 和双向 stream 测试。

禁止重新引入 Node Gateway sidecar。

---

### P0-7 Connect token 出现在 URL query

当前 pairing response 返回：

```text
/api/harnessdock/connect?token=...
```

即使 token 一次性且 90 秒过期，它仍可能进入：

- browser history；
- reverse proxy access log；
- crash/diagnostics URL；
- screenshot/share；
- referrer（如果后续页面策略变化）。

**修复**：bootstrap token 改为 POST body 或专用 exchange request，不进入 URL。

HTTPS session cookie 使用：

```text
__Host-hd_session
Secure
HttpOnly
SameSite=Strict
Path=/
```

并继续 one-time exchange + rotation。

---

### P0-8 缺 Single Instance

当前 Cargo 依赖中没有 single-instance plugin。

多开 HarnessDock 可能带来：

- 两个 Runtime；
- 多 Tray；
- Gateway 端口冲突；
- updater/restart 竞争；
- 用户误判“窗口没打开”。

**修复**：桌面端把 `tauri-plugin-single-instance` 作为第一个 plugin 注册。

secondary launch：

```text
existing Harness visible -> focus
Harness hidden in tray -> show + focus
startup/recovery -> focus current recovery
optional deep-link args -> validate -> submit HostIntent
```

---

### P0-9 Process-global PATH 被修改

当前 Desktop Adapter 为 bundled pnpm/tool 修改整个 HarnessDock 进程的 `PATH`。

**风险**：

- 后续任何 child process 都继承这个路径；
- 插件/helper 可能意外解析到 bundled tool；
- 难以证明哪一个 command 使用哪套工具链。

**修复**：删除 global PATH mutation。

新增：

```text
ExecEnvironment {
  node_path,
  dsh_entry,
  pnpm_entry,
  explicit_path,
  runtime_image_identity,
}
```

只有明确的 Runtime/plugin management child process 获得这套 env。

# 4. 当前尚未完整实现的核心功能

## 4.1 真正 Host Event Bus

当前未完成。

需要：

- host_subscribe；
- event sequence；
- state revision；
- resync；
- operation correlation；
- targeted surface delivery。

---

## 4.2 真正持续 Reconciler

当前未完成。

需要能够自动把：

```text
desired runtime ready
actual runtime stopped
```

收敛到 Ready，而不是每次都依赖某个 UI procedure 手动调用 start。

---

## 4.3 Runtime 主动 Supervisor

当前 dead process 主要在 status/specific operation 时被发现。

还缺：

- heartbeat/health probe；
- unresponsive detection；
- crash-loop counter；
- backoff；
- auto safe-mode escalation；
- resume/network change revalidation；
- orphan/leak periodic assertion。

推荐恢复策略：

```text
1st unexpected crash -> restart same mode
2nd/3rd within window -> plugin quarantine / safe mode
continued crash loop -> stop auto-restart -> RecoverySurface
```

必须设置上限，禁止死循环自恢复。

---

## 4.4 Plugin Manager 完整 Host 能力

五轮文档要求：

- plugin status；
- add/remove/update；
- quarantine；
- safe mode；
- recommended catalog；
- auto-heal。

但当前 canonical Host Protocol schema 中没有完整 Plugin/Profile 命令。

需要新增 `PluginManagerActor` 或 `PluginManagerService`，但它只负责管理，不复制 Harness UI。

安装流程必须事务化：

```text
resolve
-> download/install through bundled pinned pnpm/dsh
-> verify package/version/integrity
-> stage config
-> smoke
-> commit
-> on failure rollback
```

社区插件仍由 dsh Runtime 执行，不把第三方代码加载到 Native Host 进程。

长期如上游支持 per-plugin worker/process isolation，再接入类似 VS Code Extension Host 的隔离模型；v0.2.0 不应私自重写 dsh 插件运行时。

---

## 4.5 Profile 管理

当前 canonical protocol 未包含：

```text
profile list
profile current
profile switch
```

应作为 Host integration command 提供，但数据仍由 dsh 管理。

禁止复制第二套 Settings 数据库。

---

## 4.6 CLI shim 生命周期

文档已有目标，但当前 head 尚缺一个可由门禁直接证明的 Host-level CLI shim install/remove 生命周期。

需要：

- explicit opt-in；
- Windows/macOS/Linux platform strategy；
- 指向 packaged Runtime；
- 不复制 Runtime；
- uninstall cleanup；
- version/image identity diagnostic；
- `dsh plugin` 必须命中 packaged pinned pnpm tool。

---

## 4.7 App update post-install health / rollback guard

当前 UpdateActor 只有：

```text
Idle -> Checking -> Downloading -> Installing -> Restarting -> Idle/Failed
```

还缺：

- pre-update checkpoint；
- update operation id；
- post-restart health marker；
- first-boot-after-update detection；
- crash-loop after update special recovery；
- last-known-good metadata。

v0.2.0 不一定需要自动执行旧版本 installer 回滚，但必须至少能够识别：

> “新版本安装成功，但新版本不能完成 RuntimeReady/PrimaryVisible。”

并进入专门 Update Recovery，而不是无限自动重启。

---

## 4.8 Production diagnostics bundle

当前 startup trace 只有 phase + elapsed time，是很好的基础，但还不够定位复杂问题。

需要本地、默认无远程上传的 redacted diagnostics bundle：

```text
client version
candidate SHA
runtime manifest public fields
actor phase transitions
last N HostEvents
last errors + correlation ids
startup trace
crash-loop journal
gateway public state (no secrets)
updater phase
platform/webview/runtime versions
```

任何 URL token、session cookie、pairing ticket、authorization/header secret 都必须在 source 层禁止进入 bundle，而不是导出后再尝试删除。

---

## 4.9 Protocol compatibility negotiation

当前 Host Protocol 对非 v2 直接 reject。

同一安装包内 desktop surface 问题不大，但 Mobile/Gateway/未来独立插件会出现版本错位。

增加：

```text
protocolVersion
minCompatibleVersion
featureFlags
schemaHash
```

连接时先 negotiate；不兼容时显示明确 upgrade requirement。

---

## 4.10 External navigation / popup / download policy

Harness Web 目前重点验证主 navigation origin，但成熟客户端还需要显式定义：

- `window.open`；
- popup；
- external http/https link；
- `file:`；
- custom protocol；
- download；
- OAuth callback。

默认：

```text
managed runtime origin -> same WebView
approved external https -> system browser
file/javascript/data/custom unknown -> deny
privileged download -> local trusted flow
```

避免让 Web 内容自由改变 Native Host 的信任边界。

# 5. 三轮连续优化方案

三轮不是三次停顿，而是三个连续责任域。

```text
Optimization Round A  Control Plane + Trust Boundary
Optimization Round B  Supervision + Gateway + Plugin Transaction
Optimization Round C  Production Proof + Supply Chain + Observability
```

---

# Round A — Control Plane + Trust Boundary

## A1. 建立真正 HostKernelTask

新增：

```text
kernel/
  mod.rs
  handle.rs
  message.rs
  state.rs
  reconciler.rs
  event_bus.rs
  operation.rs
```

结构：

```text
Tauri IPC/Menu/Tray
     |
KernelHandle.send(KernelMessage)
     |
     v
HostKernelTask
  |- Capability Broker
  |- request dedupe
  |- DesiredState
  |- Reconciler
  |- Actor registry
  `- HostEvent publisher
```

Kernel task 单线程拥有 control state，尽量删除跨模块 control-state Mutex。

## A2. HostCommand 幂等

`request_id` 现在只验证格式，没有 dedupe。

新增 bounded dedupe cache：

```text
(subject, request_id, generation)
 -> previous result
```

用于处理：

- double click；
- WebView retry；
- reconnect resend；
- mobile network retry。

Update/Restart/PluginInstall 必须保证同一 request 不重复执行。

## A3. Host Protocol v2.1 event stream

schema 增加：

- HostEvent；
- HostEventKind；
- sequence；
- revision；
- OperationId；
- feature negotiation；
- public actor snapshots。

替换 settings/control polling。

## A4. Capability 拆细

# Round B — Supervision + Gateway + Plugin Transaction

## B1. RuntimeSupervisor

Supervisor 不直接 owner process；RuntimeActor 仍是 owner。

Supervisor 负责 health policy：

```text
periodic health probe
process-exit event
probe timeout
crash-loop window
recovery escalation
suspend/resume revalidation
```

引入 `BootJournal`：

```text
last_clean_shutdown
last_client_version
last_runtime_generation
consecutive_start_failures
recent_crash_timestamps
last_update_operation
```

使用原子写 + rename，内容不含 secret。

## B2. Crash-loop breaker

示例策略：

```text
unexpected crash
 -> bounded retry with backoff
 -> repeated failure -> safe mode
 -> repeated safe-mode failure -> Recovery
 -> stop automatic restart
```

具体阈值必须通过测试和真实 telemetry/baseline 决定，不在代码中散落 magic number。

## B3. Gateway 迁移成熟 HTTP stack

目标：

```text
127.0.0.1 listener
 -> hyper HTTP/1 server
 -> typed router
 -> auth middleware
 -> bounded async proxy
 -> current RuntimeLease upstream
```

必须覆盖：

- Host header policy；
- hop-by-hop header stripping；
- request/response timeout；
- body streaming；
- connection semaphore；
- WebSocket upgrade（如 Harness 需要）；
- cancellation on Gateway/Runtime stop；
- rate limit；
- no secret URL；
- current generation binding。

## B4. Gateway session 升级

- pairing code one-time；
- connect exchange POST；
- token 不进 URL；
- session cookie rotation；
- device revoke；
- revoke-all；
- generation invalidation；
- optional short idle TTL + absolute TTL；
- public URL change invalidates old bootstrap context。

## B5. Plugin transaction manager

实现：

```text
PluginList
PluginInstall
PluginRemove
PluginUpdate
PluginRollback
PluginQuarantine
PluginClearQuarantine
```

全部经 Host Protocol + trusted local surface。

插件安装失败不能破坏下一次 Harness Web 正常启动。

## B6. Profile management

实现 list/current/switch，不复制 dsh 数据。

## B7. CLI shim lifecycle

实现 install/status/remove + smoke gate。

## B8. Power/network lifecycle

Desktop resume 后：

```text
revalidate process
revalidate RuntimeLease
revalidate WebView origin
revalidate Gateway
refresh snapshot/event
```

网络变化只影响 Gateway，不得把本地 Harness Web 判为失败。

## B9. External navigation policy

把 popup/new-window/external protocol/download 明确纳入测试。

### Round B 验收

- [ ] process crash 可主动发现，不依赖用户打开 diagnostics；
- [ ] crash-loop 不会无限 restart；
- [ ] repeated failure 可以自动进入 safe/recovery；
- [ ] Gateway 不再手写 HTTP framing；
- [ ] WebSocket/streaming/timeout/security tests green；
- [ ] connect token 不进入 URL；
- [ ] Runtime restart 自动失效 Gateway generation/session；
- [ ] Plugin install/update 有 transaction + rollback；
- [ ] Profile/CLI shim 有真实 E2E；
- [ ] suspend/resume 不产生 stale lease；
- [ ] popup/download/external navigation policy 可证明。

```text

startup traces
BootJournal public subset
update state
gateway state without sessions/tokens
CI/build identity
```

## C3. Performance SLO

不要一开始硬编码拍脑袋绝对值。

先建立每个平台基线：

- process -> splash；
- Runtime verify；
- Runtime spawn -> ready；
- Runtime ready -> primary visible；
- shell injection；
- restart；
- safe-mode restart；
- gateway startup。

然后采用：

```text
absolute safety ceiling
+ relative regression budget
```

例如 CI 同硬件/同 runner 类型的 p95 退化超过基线一定比例即阻断。

## C4. Resource leak gate

Repeated 50/100 cycles：

```text
Runtime restart
Gateway start/stop
Harness show/hide/reload
Diagnostics open/close
```

检查：

- process count；
- thread count；
- socket count；
- temp file；
- WebView count；
- memory growth trend。

## C5. Fault/property/model tests

至少覆盖：

```text
stop-during-start
restart-during-probe
quit-during-update
runtime-death-during-gateway
user-close-during-restart
stale ready file
stale navigation callback
stale Gateway session
plugin install interrupted
update restart interrupted
secondary-instance during startup
resume after runtime death
```

属性不变量：

```text
<= 1 managed Runtime process
<= 1 current RuntimeLease
Gateway Ready => current RuntimeLease exists
Harness Visible => current generation matches
Quitting => no new long-lived resource may publish Ready
old generation event cannot mutate current state
remote subject cannot gain local-admin capability
```

## C6. Supply-chain provenance

当前 release 已经有 updater signature + SHA256SUMS，但继续加入：

- GitHub Artifact Attestation；
- SBOM（SPDX 或 CycloneDX）；
- installer/runtime archive provenance；
- Runtime manifest hash 纳入 attestation metadata；
- candidate SHA 与 artifact digest 可离线验证。

GitHub Artifact Attestation 可以提供可验证 build provenance；公开仓库还可结合 Sigstore transparency log。

如果后续将 reusable workflow 固化为组织级受控构建，可以进一步向 SLSA Build Level 3 的方向演进。

## C7. OS signing / notarization gate

Tauri updater signature 只证明 updater artifact 信任链，不应和 OS 平台签名混为一谈。

正式 stable 发布应分别验证：

- Windows Authenticode（如果项目提供签名证书）；
- macOS code signing + notarization；
- Android正式 release key；
- iOS正式 signing/profile（当 iOS 超出 Simulator scope 时）。

如果 v0.2.0 暂无对应证书，文档必须明确哪些 artifact 是 candidate/dev，不伪装成 production signed build。

## C8. Stable/Candidate channel

不要求立刻扩展版本号，但 release pipeline 应具备：

```text
candidate -> validation -> stable
```

禁止 stable 客户端自动安装未通过 exact-main-SHA release gate 的 candidate。

# 13. 最终评价

当前 HarnessDock 的核心方向已经不是“需要再换一次架构”，而是：

> **需要把已经设计出来的 Native Host Kernel 真正执行到底。**

下一阶段最有价值的工程工作不是继续增加外壳页面，而是把：

```text
Actor
+ Lease
+ Capability
+ Desired State
+ Reconciler
+ Event Stream
+ Supervisor
+ Release Evidence
```

连成一条单一控制链。

完成本方案后三个优化 Round，HarnessDock 才会从“有先进架构组件”升级为“具备先进客户端控制平面特征”的产品：

- Host 是唯一真相；
- WebView 是可替换、不可信的显示/交互层；
- Runtime/插件失败不会破坏 Native Host；
- 所有资源都有唯一 owner；
- 所有异步结果都可以证明属于 current generation；
- 所有动作都有 operation id、幂等、事件和恢复路径；
- Gateway 不承担自研 HTTP parser 风险；
- Release 可以证明来自哪个 commit、哪个 Runtime、哪个 workflow；
- 用户仍然默认直接进入 Harness Web，而不是进入第二套配置产品。

这应作为 v0.2.0 五轮架构之后的最终生产化优化路线。
